# Windows SSH 持续流控制帧等待输入结束

## 失败与边界

初期二进制/文本往返自测在传入完整输入并关闭stdin后通过，未证明长连接可实时传输。
保持producer打开时，接收端hello可以读出，小控制帧却无法在超时前得到响应；
普通Python SSH stdin对照可即时响应，因此不能把此现象归因网络不通或虚拟声卡。

## 修复与回归

Windows中继不再依赖.NET Console/StreamReader的标准输入缓冲，改为在自己的stdin管道上按可用字节
读取（无数据时只等待一个字节），使用Win32 PeekNamedPipe/ReadFile；不读取硬件输入或记录内容。
保留64KiB帧、90KiB行上限及CR/LF边界处理，输出固定ASCII Base64帧。
同用户命名管道采用重叠/异步双向I/O，SSH连接独立于用户既有multiplex控制进程。

已验证：新暂存程序在不关闭stdin时立即返回固定诊断数据；部署后保持同一真实SSH连接，
连续两次32000静音样本请求均在EOF之前返回自然排空确认。未触发录音键、未录用户音频。
旧标准输入路径在保持producer打开时超时；新路径的真实SSH回归和连续双轮音频回归均通过。
长期回归入口为Tests/RemoteVoiceTransportTests.py；默认只回显固定字节，--audio-probe才播放虚拟输出静音。
只在关闭输入后通过的测试不再视为持续流成功。

另修正升级过程：先安全停止桌面lease owner，再清理同用户、同安装路径下的遗留非交互中继测试进程，
避免它们锁住EXE。未知任务继续拒绝替换；现有无窗口启动包装器须先验证唯一目标和命令范围，
仅更新本组件参数，保留隐藏窗口和退出码传播。
