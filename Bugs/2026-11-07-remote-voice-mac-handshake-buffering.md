# Mac 持续 SSH 输出的小握手消息被阻塞

## 失败证据与根因

Mac 候选运行时连续四轮出现 `connection=failed reason=handshake_timeout`，本机语音仍正常。
同一 Windows 接收器经保持输入打开的 Python SSH 回归立即返回握手与固定字节回显，
因此不能据此要求重新授权蓝牙、重装声卡或修改输入法。

最小真实管道实验确认：`FileHandle.read(upToCount: 4096)` 在收到小消息时仍等待，
直到写端关闭才返回；同一管道改用 POSIX `read` 可在 EOF 前返回已有字节。
永久回归 `shortControlReplyArrivesWhilePeerRemainsOpen` 对原实现失败：一秒内没有返回握手，
关闭写端后才解除阻塞。不是通过增加握手超时来掩盖问题。

## 最小修复

SSH stdout 按非阻塞 POSIX 读取当前可用字节，每次最多 4096 字节。
暂时无数据与 EOF 分开处理；EINTR 重试，EAGAIN 不断开连接，真实读取错误使用稳定原因码。
原接收预算、连接 generation、帧长度及 Base64 行上限保持不变，不记录响应内容或 SSH 错误正文。
本机音频、Fn 按键、Windows 接收器和系统权限不在本次修复范围内。

## 验证边界

12 项路由回归通过，覆盖 EOF 前的小握手、暂时空管道、读取上限、连续字节完整性及实际 EOF。
全量 1311 项/95 套件通过，测试前后日常 App 仍为同一进程；新时序回归使用独立线程，避免全量并行时公共线程池饥饿造成误报。
直接运行当前生产传输代码连接实际 Windows 接收器，已在 EOF 前收到 `connection=ready`，
随后显式关闭该独立验证连接；没有触发语音键或采集用户声音。
真实 SSH 的传输就绪只证明消息通道，不证明 Windows 豆包已启动或文字上屏；
用户仍须完成两端短句、连续会话、长段、回切与异常恢复验收。
